# GitFinder 项目管理功能规划

## 1. 产品定位

GitFinder 从“Git 仓库管理器”扩展为“项目化的本地文件管理器”。最终目标是在 `/Volumes/project` 范围内基本接管 Finder 的日常管理职责：不只看见文件夹，还能识别它们是什么项目、处于什么状态、下一步应做什么。

产品的核心不是复制 Jira，而是结合本地代码和 Git 证据，回答五个问题：

1. 项目目前处于什么阶段？
2. 正在处理哪些任务？
3. 最近完成了什么？
4. 存在哪些阻塞、延期和风险？
5. 任务状态有哪些可验证的代码或测试证据？

同时必须满足四个文件管理结果：

- **清晰**：一眼分清开发中、已部署、学习、工具、资料和归档。
- **可管理**：可创建、移动、重命名、归档、搜索和打开内容。
- **可追踪**：项目的任务、进度、文件变化、Git 证据和决策可回溯。
- **可识别**：自动判断目录是否为项目、项目类型、技术栈、生命周期和完整度。

产品以单页桌面应用为主，Electron 仅通过受验证的 IPC 提供本地文件、Git 和终端能力。任务、进度和验收仍以项目 CSV/Markdown 事实源为主，由 Local Project Manager 的功能牌协议读写；GitFinder 负责在同一个桌面入口呈现和操作这些投影，不复制第二套业务状态。

## 2. 从 Jira 借鉴什么

| Jira 概念 | GitFinder 中的实现 | 取舍 |
|---|---|---|
| Project | 项目，可关联一个或多个本地仓库 | 不再将仓库等同于项目 |
| Epic | 里程碑或大型工作项 | 不单独增加 Epic 实体 |
| Sprint | 迭代 | 保留起止日期、目标和状态 |
| Issue | 任务 | 统一任务、Bug、需求和技术债 |
| Workflow | 固定的简化状态流 | 首版不做自定义工作流 |
| Board | 看板视图 | 与列表、时间线共用同一数据 |
| Activity | Git 与人工事件时间线 | 强调证据和可追溯性 |
| Dashboard | 跨项目进度首页 | 作为应用默认入口 |

首版不实现 Jira 的权限方案、工时账单、审批流、插件市场、多组织和复杂报表。

## 3. 信息架构

应用保留单页结构，顶层导航调整为：

- **项目总览**：跨项目健康度、阻塞、延期、近期成果。
- **任务看板**：待办、进行中、阻塞、待验证、已完成。
- **时间线**：人工操作、Git 提交、测试结果和 AI 摘要。
- **文件**：目录树、文件搜索、预览、创建、重命名、移动、归档和打开。
- **仓库**：现有状态、分支和 Git 操作，作为项目详情的专业工具页。

项目详情使用标签页：

- 概览：目标、阶段、迭代、健康度和下一步。
- 任务：列表与看板切换。
- 里程碑：计划日期、完成条件和完成率。
- 动态：可追溯的项目过程。
- 文档：README、CONTEXT.md、ADR 和修复报告。
- Git：保留现有仓库管理功能。

### 3.1 内容类型

目录扫描后，每个主要目录必须被归入一种类型：

| 类型 | 说明 | 示例 |
|---|---|---|
| 项目 | 有目标、生命周期和可交付成果 | Web 应用、脚本工具、数据项目 |
| 工具 | 为其他项目服务的本地工具 | AI 技能包、脚手架、CLI |
| 资料 | 以阅读、参考或素材为主 | 文档、图片、研究资料 |
| 学习 | 用于学习和实验，不承诺交付 | 教程代码、原型 |
| 归档 | 已结束且默认只读 | 历史项目、已废弃方案 |
| 未识别 | 证据不足，等待人工归类 | 新建或零散文件夹 |

“未识别”必须是正式状态，AI 不得为了覆盖率强行分类。

### 3.2 项目生命周期

```text
待整理 -> 已规划 -> 开发中 -> 验证中 -> 已部署 -> 维护中 -> 已归档
                         |                         |
                         +-------> 暂停 <--------+
```

生命周期与 Git 状态分离。例如，“已部署”项目可以有未提交的维护修改；仓库已同步也不代表项目已完成。

### 3.3 Finder 接管范围

首先接管 `/Volumes/project` 及用户手动添加的根目录，不尝试成为全系统 Finder 替代品。

必须提供：

- 目录树、面包屑、前进/后退和多根目录。
- 按文件名、路径、项目、类型、标签和内容元数据搜索。
- 新建文件/文件夹、重命名、移动、复制、显示于 Finder、使用默认应用打开。
- 文本、Markdown、图片和常用项目配置的快速预览。
- 文件操作历史和可恢复的撤销机制。
- 删除默认移入系统废纸篓，不提供绕过恢复的快捷永久删除。

文件移动时，应同步更新项目与仓库路径关联，并将“从哪里移到哪里”记入活动日志。

### 3.4 项目识别引擎

识别分为“硬规则事实”和“AI 语义建议”两层。

硬规则可以识别：

- `.git`、`package.json`、`pyproject.toml`、`Cargo.toml`、`go.mod` 等项目特征。
- README、CONTEXT.md、AGENTS.md、ADR、修复报告和部署文件。
- 技术栈、包管理器、启动命令、测试命令和版本号。
- 最近文件修改、最近提交、远程仓库和工作区状态。
- 顶层目录所暗示的初始分类，如“开发中”、“已部署”、“学习”和“项目存档”。

AI 只用于建议：

- 从 README 和文档提取项目用途、当前阶段和可能的下一步。
- 识别多个仓库是否属于同一个项目。
- 发现重复项目、失效副本、缺少上下文或应归档内容。
- 生成归类建议及置信度，经用户确认后生效。

## 4. 核心数据模型

### 4.1 项目与仓库分离

一个项目可以关联多个仓库，一个仓库在首版只属于一个项目。单仓库项目在首次扫描时可自动创建。

### 4.2 CSV 文件

结构化项目数据沿用 Local Project Manager 的项目事实源与功能牌协议。GitFinder 可以缓存索引，但以下 CSV 的权威副本位于对应项目管理目录中，而不是再复制到 GitFinder 用户数据目录：

| 文件 | 用途 | 关键列 |
|---|---|---|
| `projects.csv` | 项目主数据 | id, name, status, stage, priority, owner, start_date, target_date, updated_at |
| `iterations.csv` | 迭代 | id, project_id, name, goal, start_date, end_date, status |
| `tasks.csv` | 任务与 Bug | id, project_id, iteration_id, type, title, status, priority, assignee, due_date, parent_id |
| `milestones.csv` | 里程碑 | id, project_id, title, target_date, status, completion_rule |
| `activity.csv` | 追加式活动日志 | id, project_id, task_id, occurred_at, source, event_type, summary, evidence_ref |
| `task_links.csv` | 任务证据关联 | task_id, link_type, reference, created_at |
| `content_index.csv` | 目录识别索引 | path, content_type, project_id, detected_type, confidence, fingerprint, scanned_at |
| `file_operations.csv` | 文件操作历史 | id, occurred_at, operation, source_path, target_path, recoverable, status |

约束：

- ID 使用稳定 UUID，不使用行号。
- CSV 写入必须经过结构化解析器，正确处理逗号、换行和引号。
- 写入采用临时文件加原子替换，避免崩溃损坏。
- `activity.csv` 只追加，不重写历史语义。
- 业务 CSV 默认不放入被管理的项目仓库，避免污染工作区。
- 可为单个项目选择“导出到仓库”，用于团队共享。

## 5. 任务工作流

首版固定五个状态：

```text
待办 -> 进行中 -> 待验证 -> 已完成
             |          |
             +-> 阻塞 <-+
```

状态规则：

- 任务开始时记录人工事件。
- 关联提交后可由 AI 建议进入“待验证”，不自动标记“已完成”。
- 测试通过不等于业务验收通过。
- Bug 在用户确认有效后才标记完成，并触发 `/Volumes/project/修复报告/` 归档提醒。
- 任务完成必须保留至少一个证据：提交、PR、测试结果、文档或人工验收记录。

## 6. AI 自动记录

AI 不直接修改项目事实，而是在事实采集之上生成建议。

### 可自动写入的事实

- 提交 hash、作者、时间和提交信息。
- 分支变化、未提交文件数、待推送和待拉取状态。
- 测试或构建命令、结果和退出码。
- 任务的人工创建、编辑和状态变更。

### 必须经过确认的 AI 建议

- 将提交关联到某个任务。
- 将任务移动到“待验证”或“已完成”。
- 生成阶段摘要、风险和下一步。
- 从非结构化文档中创建任务。

所有 AI 结果显示三项内容：结论、证据、置信度。用户接受后才写入业务 CSV；拒绝结果也记入活动日志，便于以后调整规则。

## 7. 项目总览指标

总览页不以提交数作为进度。核心指标为：

- 当前迭代已完成任务数 / 总任务数。
- 按优先级加权的完成度。
- 阻塞任务数和最长阻塞时间。
- 逾期任务和近 7 日到期任务。
- 里程碑完成率与日期风险。
- 最近一次有效活动时间。
- 没有明确任务的活跃代码变更。

当项目没有任务或里程碑时，显示“尚未规划”，不生成虚假的精确百分比。

## 8. 分期实施

截至 2026-08-26，阶段 0 的本地可靠性、安全边界与 Local Project Manager schema 1.1 接入已完成首轮；阶段 2 已具备跨项目任务总览、筛选、列表/状态看板、验收/证据、项目下钻、任务/里程碑权威写回、六字段任务编辑和跨项目任务创建；阶段 3 已具备普通文件显示、安全预览、全局搜索、安全新建文件/文件夹、复制/粘贴、重命名、批量移动、受管目录内移动拖放、Finder/桌面外部复制导入、系统废纸篓、撤销、可恢复标签页和标签页重排；阶段 4 已具备逐文件 diff、暂存/取消暂存、仅提交已暂存内容、任务关联仓库的严格归因只读 Git 实况，以及跨项目持久化活动、测试、验收和自动化时间线。尚未完成的重点包括大目录持久化增量索引和跨卷风险提示。

### 阶段 0：可靠性与连接基础

目标：先让仓库身份、路径、配置和本地连接可信，再接入既有项目事实源。

- 修复仓库稳定身份、路径移动重绑定、分类统计和批量 Git 状态。
- 配置与注册表使用原子写入、损坏备份和数据校验。
- 收紧 Electron、IPC、Git 参数、终端和可选 Web 服务的安全边界。
- 接入 Local Project Manager 的项目/任务/里程碑/证据读取合同。
- 为解析、路径迁移、损坏恢复和安全边界建立测试。

验收：关闭并重开应用后数据一致；提交和目录移动不破坏关联；异常中断不会覆盖最后一份有效配置；GitFinder 不维护第二套任务事实。

### 阶段 1：内容识别与项目注册

目标：让 `/Volumes/project` 中的主要内容清晰、可识别。

- 扫描并建立内容索引，不依赖 Git 才能显示。
- 按硬规则识别项目、工具、资料、学习、归档和未识别目录。
- 从顶层目录导入初始生命周期，但允许人工修正。
- 将已扫描 Git 仓库注册为项目或项目组成部分。
- 提供“待整理”收件箱，集中处理未识别和信息不完整内容。

验收：所有扫描到的主要目录均显示内容类型或“未识别”；所有分类结果均能查看判定证据。

### 阶段 2：项目与任务 MVP

目标：不离开 GitFinder 界面完成每日项目管理，底层仍保持单一事实源。

- 首页改为项目总览。
- 创建、编辑、归档项目，并关联现有仓库。
- 创建、编辑、排序和筛选任务。
- 提供列表和看板两种任务视图。
- 支持迭代、里程碑和阻塞原因。
- 保留原有仓库视图和详情操作。

验收：用户可从项目总览进入项目，创建任务，在看板中推进状态，并在重启后看到完整历史。

### 阶段 3：文件管理接管

目标：日常整理 `/Volumes/project` 时无需切换到 Finder。

- 补齐创建、重命名、移动、复制、归档、废纸篓和预览。
- 为项目移动提供专用操作，同步更新路径索引和项目关联。
- 对未提交仓库、运行中项目和跨卷移动给出明确风险提示。
- 记录所有文件管理操作，可恢复的操作提供撤销。

验收：可以在应用中完成项目新建、重命名、移入归档和恢复，项目记录与实际路径始终一致。

### 阶段 4：Git 证据和自动时间线

目标：让项目进度与实际开发活动自动对齐。

- 扫描时记录 Git 状态变化，相同状态不重复写入。
- 根据任务 ID 规则关联提交，例如 `GF-123`。
- 允许手动关联或解除提交证据。
- 记录测试和构建结果。
- 提供项目与跨项目时间线。

验收：产生提交或工作区变化后，下次扫描能产生一条可追溯活动；无变化扫描不产生日志噪音。

### 阶段 5：AI 项目助手

目标：减少人工整理，不牺牲可验证性。

- 生成每日、每周和迭代摘要。
- 识别长期无活动、代码活跃但任务未更新、里程碑日期风险。
- 提出任务状态和提交关联建议。
- 所有写入业务数据的 AI 操作需人工确认。
- 保留模型、时间、输入证据和接受/拒绝结果。

验收：AI 摘要的每个完成项都可打开对应证据；AI 不会在无确认时关闭任务。

### 阶段 6：报表与交付

- 迭代完成趋势、阻塞时长和里程碑预测。
- 导出单项目 Markdown/HTML 进度报告。
- 生成可用于交接的项目快照。
- 可选与 GitHub Issues 双向同步，不作为本地数据的必要依赖。

## 9. 技术改造边界

优先复用现有模块：

- `fileService` 继续负责项目文件与目录。
- `gitService` 继续负责 Git 状态与证据采集。
- `configService` 只保存界面偏好和扫描配置，不承担项目业务数据。
- 新增 `projectService`、`taskService`、`activityService` 和共用 `csvStore`。
- 上述项目服务优先作为 Local Project Manager 连接器/内嵌模块实现；除非另有迁移 ADR，不在 GitFinder 内创建第二份权威 CSV。
- 渲染层将项目功能按模块拆分，避免继续扩大当前单一 `app.js`。

安全边界：渲染层不直接访问文件系统；所有路径、CSV 文件名和 Git 参数在主进程验证；AI 不直接获得任意文件读写权限。

## 10. 当前切片与下一步

v1.16.0 交付工作区标签页重排。拖动标签时原位提供半透明反馈，跨越其他标签中点即连续调整预览顺序，靠近滚动区边缘会自动滚动；释放后保持活动标签与各页路径、历史、搜索和类型筛选状态，立即持久化。键盘用户可用 `⌥⇧←/→` 完成同一操作，减少动态效果设置下取消位移动画。

本切片已经满足“Local Project Manager 权威写回合同”：

1. 为每个已注册项目提供无副作用的任务创建、任务状态/字段和里程碑字段变更预览，而不是让 GitFinder 直接写 CSV。
2. 请求必须校验项目、对象 ID、阶段、父任务、当前事实、字段白名单、字段值和修订号，并返回结构化差异、影响文件与验证结果。
3. 只有 GitFinder 中的人工确认才调用应用接口；Local Project Manager 负责原子写入、备份、投影重建和幂等操作记录。
4. 适配器对登记项目通用，使用受管根/项目身份校验、进程锁、自动备份、活动审计、投影重建、失败回滚和 operation id 幂等保护。

此前交付的里程碑应用仍会逐字段追加 `plan_changes.csv` 并记录人工活动；选择“已验收完成”不会由自动检查代替人工决定。下一切片优先处理大目录持久化增量索引和可取消进度反馈；任何新增项目写操作仍继续复用权威边界，并分别定义可审查的字段合同。

## 11. 决策建议

推荐按“阶段 0 + Finder 文件操作垂直切片”启动，先完成可靠身份、安全边界与可恢复文件管理，再接入项目任务看板。结构化项目管理复用 Local Project Manager，不重新开发一套平行事实源。

原因是 AI 需要稳定的任务、状态和活动模型作为上下文。如果先做 AI 摘要，但没有可靠的项目数据模型，应用仍然只是“会总结 Git 的仓库管理器”，不会成为项目管理工具。
