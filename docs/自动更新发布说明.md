# GitFinder 自动更新与正式发布说明

当前应用版本统一来自 `package.json`。打包应用启动约 10 秒后自动检查更新，也可以点击界面中的版本号或“检查更新”按钮手动检查；下载完成后可选择“重启安装”。更新源固定为 GitHub Releases：

```text
https://github.com/goldf2/git-status-monitor/releases
```

## 两种构建模式

### 开发构建

```bash
npm run dist
```

默认构建使用 ad-hoc 签名，只用于本机开发和桌面验收。构建结束会生成 `dist/release-verification.json`，其中必须满足：

```json
{
  "mode": "development",
  "eligibleForDistribution": false
}
```

开发门禁仍会检查版本、Bundle ID、arm64 架构、打包内容、图标、ZIP 完整性以及 `latest-mac.yml` 的文件名、大小和 SHA-512。`eligibleForDistribution: false` 不是失败，而是明确禁止把 ad-hoc 包冒充正式 Release。

### 正式发布

正式发布只能从与 `package.json` 完全一致的 Git 标签构建，并必须同时满足：

- `package.json`、`package-lock.json` 根包、App Bundle、`app.asar` 和 Git 标签版本一致。
- 工作区干净，发布标签指向当前提交。
- Bundle ID 固定为 `com.gitfinder.app`，三平台图标格式正确，构建内 ICNS 与源图标哈希一致。
- macOS 主程序是 arm64 Mach-O；ZIP 完整且只包含根目录 `GitFinder.app`。
- 使用 `Developer ID Application` 身份签名，TeamIdentifier 与发布团队一致。
- 签名启用 Hardened Runtime、包含安全时间戳，且不含 `com.apple.security.get-task-allow=true`。
- 严格深度 codesign、Gatekeeper `spctl` 与 `xcrun stapler validate` 全部通过。
- `latest-mac.yml` 与最终 ZIP 的名称、版本、大小和 Base64 SHA-512 完全一致。

只有上述条件全部成立时，验证报告才会写入：

```json
{
  "mode": "official",
  "eligibleForDistribution": true,
  "issues": []
}
```

## GitHub Secrets

仓库的 Release workflow 需要配置以下 Secrets：

| Secret | 内容 |
|---|---|
| `MACOS_CERTIFICATE_P12` | 含 Developer ID Application 证书和私钥的 `.p12` 文件 Base64 内容 |
| `MACOS_CERTIFICATE_PASSWORD` | 导出 `.p12` 时设置的密码 |
| `MACOS_SIGNING_IDENTITY` | 完整签名身份，例如 `Developer ID Application: Company Name (TEAMID)` |
| `APPLE_ID` | Apple Developer 账号 |
| `APPLE_APP_SPECIFIC_PASSWORD` | Apple ID 的 App 专用密码 |
| `APPLE_TEAM_ID` | Apple Developer Team ID |

证书、私钥、密码和 Apple ID 不得写入源码、`.env`、构建报告或 Release 附件。工作流会把证书和公证凭据导入 runner 的临时 Keychain；构建脚本只接收签名身份、Team ID 和 Keychain profile，不接收公证密码。工作流结束时删除临时证书文件和 Keychain。

## 发布新版本

1. 使用语义化版本递增 `package.json` 与 `package-lock.json`，保持三处版本声明一致。
2. 执行完整检查：

```bash
npm run check
npm run verify:release-source
git diff --check
```

3. 提交全部发布源码，确认工作区干净。
4. 创建与版本完全一致的标签，例如：

```bash
git tag v1.25.0
git push origin main
git push origin v1.25.0
```

5. `.github/workflows/release.yml` 在 macOS runner 上执行测试、源码门禁、临时 Keychain 导入、Developer ID 签名、Apple 公证、产物门禁，最后才创建或更新 GitHub Release。
6. Release 必须同时包含：

```text
GitFinder-<版本>-arm64-mac.zip
latest-mac.yml
release-verification.json
```

`workflow_dispatch` 只能在选择版本标签作为 ref 时生成发布；从普通分支手动运行会跳过发布作业。

## 本机正式构建

本机已经安装 Developer ID Application 证书时，可先把公证凭据安全存入 Keychain。省略 `--password` 后 `notarytool` 会交互式读取 App 专用密码：

```bash
xcrun notarytool store-credentials gitfinder-notary \
  --apple-id "<Apple ID>" \
  --team-id "<Team ID>"
```

然后在干净、已检出对应版本标签的工作区执行：

```bash
GITFINDER_RELEASE_MODE=official \
GITFINDER_EXPECTED_TAG=v1.25.0 \
GITFINDER_CODESIGN_IDENTITY="Developer ID Application: Company Name (TEAMID)" \
GITFINDER_NOTARY_KEYCHAIN_PROFILE=gitfinder-notary \
APPLE_TEAM_ID=TEAMID \
npm run dist
```

若证书或公证 profile 位于非默认 Keychain，再额外设置 `GITFINDER_CODESIGN_KEYCHAIN=/absolute/path/to/keychain-db`。不要把上述真实值保存进仓库脚本。

## 门禁命令

```bash
# 只检查当前源码；开发模式不要求标签和干净工作区
node scripts/verify-release.js --phase source --mode development

# 复核已经生成的本机开发产物
npm run verify:release

# CI 使用的正式源码门禁示例
node scripts/verify-release.js \
  --phase source \
  --mode official \
  --expected-tag v1.25.0
```

正式产物验证由 `scripts/build-mac.sh` 自动执行，不建议跳过脚本手动组装附件。更新源文件 `resources/app-update.yml` 在签名和公证之前进入 App；签名后不得再修改 App Bundle，否则签名和公证资格都会失效。

## 当前边界

- 没有 Apple Developer 凭据时只能生成本机开发包，不能得到 `eligibleForDistribution: true`。
- Windows 由真实 `windows-latest` runner 同时生成 NSIS 安装包和 ZIP；未配置或未通过 Authenticode 时只能作为未签名测试版，并明确保留 SmartScreen 风险，不能进入稳定 Release。
- 从普通分支手动运行发布流程时，`publish_unsigned_windows` 默认为关闭：关闭时只保留 Actions 附件；明确开启后，只有通过全部 Windows 验收且签名状态不是 `Valid` 的产物，才会发布到 `windows-v<版本>-test1` 预发布页。该入口不会创建稳定 Release，也不会把未签名产物描述为正式版。
- 首个正式 macOS Release 仍应在另一台没有开发环境和旧 Keychain 状态的 Mac 上，从实际下载的 ZIP 完成安装、启动和自动更新验收。
