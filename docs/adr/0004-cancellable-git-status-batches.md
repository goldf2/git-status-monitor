# ADR 0004：大量仓库状态使用受控并发、可取消批次

- 状态：已接受
- 日期：2026-08-27

## 背景

GitFinder 需要在项目模式一次展示大量本地 Git 仓库。旧实现在渲染层手写 6 个 worker，但主进程的 `batchStatus` 仍对所有路径直接 `Promise.all`，两条路径无统一边界。快速连续刷新还会让旧请求继续占用 Git 子进程，并可能在新请求后覆盖界面。

## 决策

1. 主进程是批量 Git 状态并发的唯一权威边界。默认并发数为 6，调用方可在 1–12 之间请求；单次最多 1,000 个去重后的绝对路径。
2. 批次路径必须通过真实路径的受管根目录校验。渲染页不能利用批次 API 读取未授权目录。
3. 批次默认 `autoFetch: false`。状态刷新只读本地 Git 数据，不隐式访问网络；拉取、推送和 fetch 继续由用户显式确认。
4. 每个批次使用独立请求 ID 和 `AbortController`。取消后不再启动排队仓库，并将 signal 传入正在运行的 `git` 子进程；已完成结果可保留。
5. 主进程通过受信 IPC 发送已完成、运行中、待处理、取消和最新结果。进度只存于当前会话，不写入配置。
6. 渲染层仅接受当前请求 ID 的进度和结果。新刷新先取消旧批次；旧事件、旧元数据和旧完成回调不得落地到新界面。
7. 分类、标签和 README 仍是本地元数据读取，可与 Git 批次并行；合并时不得覆盖已到达的 Git 状态。

## 结果

- 仓库数量增大时，Git 子进程数受主进程统一限制，不会随仓库数线性爆发。
- 状态栏可见展示实时进度和取消入口，连续刷新不再允许旧结果回写。
- 状态只反映已知本地与 upstream 的关系；如需最新远程事实，用户仍必须显式 fetch。
